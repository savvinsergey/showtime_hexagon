
# Engineering conventions (single source of truth for subagents)

Concrete good-vs-bad code examples for these rules are in `.agents/rules/engineering-examples.md`.

If anything here conflicts with `AGENTS.md`, `AGENTS.md` wins. If an installed skill (e.g. `angular-developer`) conflicts with this file, this file wins.

## Engineering principles
- **SOLID**
  - Single responsibility: one reason to change per class/component/function (UI component renders and delegates; use case orchestrates; domain holds rules; adapter talks to the outside world).
  - Open/closed: extend via new implementations of a port or new components, not by editing stable code with more flags/conditions.
  - Liskov: implementations of a port honour its full contract (inputs, outputs, errors).
  - Interface segregation: small, focused ports/interfaces; no fat interfaces that force unused members.
  - Dependency inversion: depend on abstractions (ports/`InjectionToken`s), never on concrete adapters from domain/application layers.
- **KISS**: the simplest design that satisfies the scenarios; avoid clever code and needless indirection.
- **DRY**: remove real duplication of knowledge (rules, mappings, types); do not merge code that merely looks similar but changes for different reasons. Extract on the third occurrence, not the first.
- **YAGNI**: implement only what the OpenSpec scenarios / task require. No speculative abstractions, options, generic layers, or "future" hooks.

## Architecture (Hexagonal / DDD)
- Domain: pure TypeScript, no framework, no I/O. Application: use cases, input/output ports. Adapters: UI, HTTP/API, persistence. Dependencies point inward only.
- Ports are injectable abstract classes or `InjectionToken`s; adapters are bound through `provideX()` helpers.
- Respect Nx module boundaries (tags / `@nx/enforce-module-boundaries`); no circular dependencies. One library per layer where appropriate (domain, application, infrastructure, ui, feature).
- Value-object boundary: a value with an invariant that can fail on user input is a branded type with a smart constructor returning `Result` (`Email`, `FullName`); an identifier is a branded type without validation (`asUserId(raw)`); a closed set is a string-literal union with no constructor (`UserRole`, `UserStatus`, parsed from the API by type guards in the infrastructure mapper); when a template must iterate that set, pair the union with an `as const` object. Do not add a TypeScript `enum`, except the explicitly approved shared operation lifecycle `OperationStatusEnum` (`idle`, `loading`, `success`, `error`, `cancelled`) and application-owned `UsersErrorKindEnum` (`validation`, `not-found`, `conflict`, `forbidden`, `network`, `unknown`). `UsersErrorKindEnum` lives only in `libs/users/application/src/lib/enums/users-error-kind/users-error-kind.enum.ts`, with colocated `.enum.spec.ts` tests, and is exported through the application public entry. `UserRole` and `UserStatus` remain string-literal unions. Everything else is a plain type (dates as ISO strings). Do not wrap fields without an invariant.
- A type used by one file stays in that file. A view model used as an `input()` or `output()` is exported from the component file. A type shared by several files of one library lives in that library. Place established framework-neutral contracts shared by multiple contexts in `shared/kernel`. Keep context-specific errors, entities, ports and events with their owner. Contexts communicate through the owner's public integration contracts. Kernel has one public entry, `@showtime/shared/kernel`; its symbol-level framework boundaries are defined below.
- Input models (`NewUser`) carry raw strings; the domain service validates and builds the model and returns `Result` with errors, so UI and application never parse domain values. When the backend assigns ids, creation is two steps: the domain builds a validated `UserDraft` (`Omit<User, 'id'>`), the repository `create(draft)` returns the `User`, and events that need the id (`UserRegistered`) are built afterwards. Domain functions take the current time as an argument (`now`), never read a clock.
- Domain models are immutable plain data types (`Readonly<{...}>`, branded value types with smart constructors returning `Result`), never classes, so one and the same model (e.g. `User`) is used across all layers and stays serializable. The domain knows only its own models: input/query models (e.g. `NewUser`, `UsersQuery`) are application-level.
- Domain behavior lives in domain services (`domain/src/lib/services`), one service per bounded context unless it genuinely splits: stateless, pure TypeScript functions/objects that take a model and return a new one (e.g. `deactivate(user)` returning `{ user, events }`, `changeRole(user, role)` returning `Result<{ user, events }, DomainError>`) and enforce structural invariants only. No `inject()`, no ports, no I/O; required data is passed as arguments. Orchestration (calling repositories/state ports, then applying domain services) stays in application use cases. The backend is the source of truth for business rules: the frontend domain validates only the structure of input (format, non-empty/length, allowed values) for fast feedback and expresses state transitions as thin named functions that emit events. Do not reimplement rules the server decides (uniqueness, permissions, state that depends on other records) and do not write predicates like `canDeactivate`; if the UI must hide actions, rely on capability flags returned by the backend (e.g. `allowedActions`). Always handle backend rejections (409/422/403) through `<Context>Error`, even when frontend validation passed. Structural validators live inside the domain service file as private functions. There is no separate `policies/` folder: split rules into their own files only when the service file outgrows ~300 lines or a second domain service appears: then group pure rule functions by meaning in `domain/src/lib/services/rules/<topic>.rules.ts` (e.g. `user-lifecycle.rules.ts`), keep the domain service as the thin public entry point that imports them (its public API and the exports from `index.ts` do not change), and move rule tests into `<topic>.rules.spec.ts`. An application service (driving-port implementation) is not a domain service.
- Domain events are plain immutable facts in past tense (`type`, `occurredAt`, ids). Domain services return them together with the result; the domain never publishes them. Use cases publish only after a successful save.
- Cross-context communication goes only through integration events: public, versioned (`<context>.<event>.v1`), primitives/ids only, declared in `libs/<context>/contracts` (`type:contracts`) and published on the shared event bus (`EVENT_BUS` from the utility lib `libs/shared/event-bus`, `type:util`, usable from the application layer of any context; the token is `providedIn: 'root'` with an in-memory factory, there is no `provideEventBus()` to register twice, and tests override the token via `TestBed` providers). Create `contracts` and `event-bus` libs and publishing only together with the first real subscriber (not speculatively); domain services return domain events from the start. A context may depend on another context only via its `contracts`; handlers are idempotent, subscribe in provider initializers, unsubscribe via `DestroyRef`, and must not break the publisher.
- Errors: the domain has only validation/invariant errors (`DomainError`). The application layer owns one error model per context (`<Context>Error`, a discriminated union by `kind`: `validation`, `not-found`, `conflict`, `forbidden`, `network`, `unknown`); use cases map domain errors to `validation`, infrastructure adapters translate transport errors (HTTP status codes) into it and return `Result` instead of throwing. Feature shows messages by `kind` and never sees HTTP.
- Each context has a single repository port for both commands and queries, declared in `application/ports/driven` (ports belong to the application side).
- Mapping to a wire format exists only in infrastructure adapters (`Model <-> ApiDto` in the HTTP adapter). There are no DTOs or mappers in application, state or domain.
- Driving (inbound) ports live in `application/ports` and are the only public API of the application layer; an application service implements them and delegates to internal use cases. They speak in domain models plus application models (`NewUser`, `UsersQuery`, ...). Feature depends only on the application layer: the driving port (via its token) and model types; application re-exports the domain model types it exposes (`export type { User } from '<domain>'`), so feature never imports domain or infrastructure.
- Adapters are bound to ports only in the composition root (the remote app named after the context, e.g. `apps/users` with federation name `users`, wraps the feature routes with `provideXApi()` / `provideXMock()`, `provideXState()` and `provideXApplication()`; feature routes declare no providers); application and feature know nothing about concrete adapters. Application must never import infrastructure.
- Driven (outbound) ports (repository, state) live in `application/ports` (they use application models such as `UsersQuery`); use cases call them via `inject(TOKEN)`. All data access (HTTP) is initiated by use cases through the repository port; adapters never fetch on their own initiative.
- `type:ui` components are dumb: no `inject()` of application services, no dependency on domain or application; inputs/outputs are described by the component's own types (view models); the smart `feature` layer maps domain models to them.
- An `output()` names the intention (`addToCart`), not the work the parent will do (`saveAndNavigate`).
- Do not pass the same data through more than two parent components. Introduce an intermediate container or the page UI service instead.
- A self-contained feature widget (comments, notifications) is its own container with its own UI service. Keep its internal state there. Its presentational children stay dumb.

### Shared kernel structure and imports
- Kernel has one public entry: `@showtime/shared/kernel`. External consumers use this entry; internal kernel imports may be relative.
- Group `src/lib` by purpose: `types/`, `enums/`, `tokens/`, `constants/`. Each entity has its own named folder with colocated tests (`<group>/<name>/<name>.ts` and `<name>.spec.ts`).
- Each entity has one authoritative definition. The public barrel exports it; a move updates imports, exports and tests and removes the old definition.
- Domain and framework-free kernel sources may use only symbols whose transitive dependencies exclude Angular and RxJS. This applies to type/value imports and re-exports, including renamed symbols and intermediary modules. Use named imports; namespace imports and export-all from the mixed public barrel are rejected in framework-free sources.
- Application imports Angular-dependent `CLOCK` and `UseCaseCall` through the same public entry. Angular core is allowed only in kernel tokens and the `UseCaseCall` contract; Angular test helpers are allowed in their colocated specs. RxJS remains forbidden throughout kernel.
- Operation lifecycle values have one pure enum definition in `enums/operation-status/operation-status.enum.ts`, exported through `@showtime/shared/kernel`. `OperationStatus<E>` uses its members as discriminants and requires `error: E` only for `OperationStatusEnum.Error`. Enum files and tests use the `.enum.ts` / `.enum.spec.ts` suffixes.
- Current clock definitions: `Clock` and `fixedClock` in `types/clock`, `CLOCK` in `tokens/clock`, `systemClock` in `constants/clock`. Do not duplicate these definitions across groups.

### State management (NgRx SignalStore for data, plain signals for UI, statuses from the application service)
- Data state: NgRx SignalStore (`@ngrx/signals`, `withEntities`) is an infrastructure detail, allowed only in the dedicated state infrastructure library (`<context>/infrastructure/state`; data access lives in a separate `<context>/infrastructure/api`, both under the `<context>/infrastructure` group folder, so each can be swapped independently; the repository mock adapter is named `<Context>MockAdapter`; adapter/provider names stay store-neutral, e.g. `UsersStateAdapter`, `provideUsersState()`). There is no global root store. `@ngrx/signals` is forbidden outside `infrastructure/state` (ESLint).
- Access to data state goes only through the state port declared in `application/ports` (e.g. `UsersStatePort` + `USERS_STATE`). Use cases inject the port by token; nobody outside infrastructure injects the SignalStore.
- The port exposes read state as Angular `Signal<T>` (like all other application ports; no custom `Readable` type; the adapter returns store signals as is) and synchronous mutation commands (e.g. `setPage`). The store keeps only the last loaded page; mutations never patch it, the application service reloads the list instead. No `Observable` or `Promise` in the port. The port and the SignalStore hold only data (entities, totals) and its internal state model stays inside `infrastructure/state`; never UI state (query, selection, dialogs) or operation status.
- Operation status: the application service is a facade over all use cases and their statuses. Statuses describe the async operations of the application layer itself (not UI); feature services map them to UI state. Every driving-port command returns the shared `UseCaseCall<T, E>` from `@showtime/shared/kernel`. Users commands specialize it as `UseCaseCall<T, UsersError>` with a read-only `Signal<OperationStatus<UsersError>>` and a `Promise<Result<T, UsersError>>`. Each call has its own status (`idle | loading | success | error | cancelled` plus the `UsersError`) set by the service (`loading` on start, then `success`/`error` from the use case result, `cancelled` for a superseded request). UI reads `call.status`; `result` is used only for navigation and reacting to success and never to derive loading/error. Queries expose `listStatus` for the latest list load, including the automatic reload the service runs after successful create/update/deactivate. Race protection (latest request wins) lives in the service; a stale call is `cancelled` and writes no data.
- UI state: every feature component (page/container) has exactly one UI service (`@Injectable()`, plain `signal`/`computed`, no `@ngrx/signals`), located next to the component (`<component>.store.ts`) and provided in the component's `providers`. It holds that feature's internal UI state (query, selected id, dialogs, local flags) and derives `loading`/`error`/`isSubmitting` with `computed` from `UseCaseCall.status` / `listStatus` instead of keeping its own flags. Dumb `ui` components keep no UI state of their own and receive it via inputs (e.g. `loading = input(false)`).
- SignalStore methods are synchronous mutations (`patchState`, `setAllEntities`): no HTTP, no repository, no `rxMethod` effects.
- State holds only serializable plain objects; domain models are plain data, so they are stored as is, without mapping. Never store class instances.
- Provide the data store through `provide<Context>State()` in the composition root and bind the port token there. Test the SignalStore directly via `TestBed`, and test use cases against the port mocks from `application/mock`.

## Angular 22 (zoneless-ready, strict)
- Standalone components only; no new NgModules; `imports: []` lists only what the template uses.
- State with `signal`, `computed`, `effect`. Shared data state may be backed by NgRx SignalStore only behind a state port in the infrastructure layer, and feature UI state by plain signals in a per-component UI service (see "State management"); outside these places only signals are visible. Inputs/outputs via `input()`, `input.required()`, `model()`, `output()`.
- Debounce of user input (e.g. search) is done in the UI with Signal Forms field debounce, not with RxJS; use cases receive the settled value.
- Async data via `resource()` / `rxResource()`. RxJS only for complex event streams (e.g. websockets, multi-source merges; not for debounce, see above); never nested subscribes; correct operator (`switchMap` latest wins, `concatMap` ordered, `exhaustMap` ignore while running, `mergeMap` parallel); side effects in `tap()`; `shareReplay({ bufferSize: 1, refCount: true })`, never plain `shareReplay()`.
- Forbidden: `toSignal()`, `toObservable()`, the `async` pipe, reactive forms (`FormGroup`, `FormControl`, `FormBuilder`), template-driven `ngModel`, `*ngIf` / `*ngFor` / `ngSwitch`, constructor DI in new code, `$any()` / `as any`.
- Forms: Angular Signal Forms with a typed `signal<T>()` model; typed validators.
- Templates: `@if`, `@for` (always with a stable `track`, not index when an id exists), `@switch`, `@empty`, `@let`; `$event` typed. When the template is longer than 5 lines, put all of its HTML in `<component>.html` next to the component and reference it with `templateUrl`. A template of 5 lines or fewer may stay inline. Do not split one component's markup between an inline `template` and an HTML file.
- Search, filter, sort and paging of a list are a chain of `computed` signals. Do not build that list in a method the template calls.
- A calculation that belongs to one component is a `computed`. Formatting reused across components is a pure pipe. A method in the template is only a trivial expression.
- Owned components use the implicit Angular 22 OnPush strategy. Omit strategy metadata unless the component needs an explicit override. Use immutable updates for inputs and arrays.
- One component per folder. The folder name matches the component file (`status-badge/status-badge.ts`, `shows-page/shows-page.ts`). That folder holds the component, its `*.spec.ts`, and files that exist only for it (a split template or styles, and the page UI store `<component>.store.ts`). Do not place several component files side by side in `src/lib`. The library barrel (`src/index.ts`) imports each component from its folder.
- DI via `inject()` at field level; teardown via `inject(DestroyRef)` / `takeUntilDestroyed()`; no manual `OnDestroy` + `Subscription` arrays. `providedIn: 'root'` is for a stateless service or for state that must survive navigation. Page UI state is provided on the component. A heavy service used by one flow is loaded with `injectAsync(() => import('...'))` instead of being pulled into the root bundle.
- Routing: `loadComponent` for standalone routes; route-scoped `providers` are allowed in the composition root (adapters/application providers) and for per-component UI services, but feature routes never bind ports or adapters; `@defer` (with `@placeholder` and `@loading`) for heavy widgets.
- TypeScript: `strict`, `strictTemplates`; no `any` (use `unknown` and narrow).

## UI
- spartan UI components only from `@shared/spartan-ui` (`libs/shared/spartan-ui/src/index.ts`, a barrel re-exporting every `@spartan-ng/helm/*` library; add a line there when a new helm library is added), never from `@spartan-ng/helm/...` directly.
- Reusable dumb components without domain knowledge (status badge with a tone, confirm dialog, loading/error/empty state wrapper) live in `libs/shared/ui` (`@shared/ui`, `type:ui`, `scope:shared`, selector prefix `st-`), built on `@shared/spartan-ui`, with `input()`/`output()` only and own simple types (no application or domain types such as `OperationStatus`); create them there from the start. Everything else (search field, pagination, data table) stays in the context's `ui` lib and moves to `shared/ui` only when a second consumer appears; design its API so the move needs no changes. `shared/ui` depends only on `@shared/spartan-ui` and util; context `ui` libs may depend on `@shared/ui`.
- Our styles are BEM classes in the component SCSS (`block`, `block__element`, `block--modifier`), with Tailwind utilities applied through `@apply`. Do not put utility classes on the template for our own styling, and do not assemble them with `hlm(...)`. Spartan directives stay on the element. Do not use `::ng-deep`. Theme with Tailwind and CSS variables.
- New motion uses `animate.enter` / `animate.leave` or a CSS transition. Do not add `@angular/animations` triggers.
- A long list is paged or virtualized with `@angular/cdk/scrolling`. Do not render an unbounded set of rows.
- Accessibility basics: labels, roles, keyboard support.

## Documentation (JSDoc)
- JSDoc (`/** ... */`) for all new or changed public API: classes, components, directives, pipes, services, use cases, ports/interfaces, public methods, exported functions, types, injection tokens.
- State purpose (the "why"), plus `@param name - description`, `@returns`, `@throws`, `@example`, `@deprecated` where relevant; no `{type}` in tags.
- Document signal `input()` / `model()` / `output()` members with one line each; document ports with their contract; adapters reference their port via `{@link PortName}`.
- Keep docs accurate when behavior changes; skip trivial private members; no noisy or redundant comments.

## Testing
- `TestBed.configureTestingModule({ imports: [StandaloneComponent] })`; never declare standalone components; `provideZonelessChangeDetection()`.
- Set signal inputs via `fixture.componentRef.setInput(...)`; interact through `@angular/cdk/testing` harnesses; never assert on `innerHTML` / `classList` or on component fields that map to DOM behavior. Test behavior, not state.
- Mock at the HTTP boundary with `HttpTestingController` (`verify()` in `afterEach`); prefer mocks/fakes over spy chains; domain tests are pure.
- Two test levels for a context: (1) application unit tests use port mocks from the separate entry point `@showtime/<context>/application/mock` (`<Context>StateMock`, `<Entity>RepositoryMock`, `provide<Context>PortsMock()`, shared port contract suites), because application must never import infrastructure (not even in specs); (2) integration tests live in the composition root app and wire the real chain with `provide<Context>Mock()` (the runtime `<Context>MockAdapter`) + `provide<Context>State()` + `provide<Context>Application()`. Contract suites from `application/mock` also run against the real adapters. `application/mock` may be imported only from `*.spec.ts` and `mock/` folders (ESLint).
- Async via `await fixture.whenStable()` or `fakeAsync` + `tick()`; never real `setTimeout`.
- Name tests after OpenSpec scenarios where they exist; cover happy path, edge cases, and error paths.

## Lint enforcement
`eslint.conventions.mjs` (spread into app/lib ESLint configs) enforces: no reactive/template-driven forms, no `toSignal`/`toObservable`, no `CommonModule`/`NgIf`/`NgFor`/`AsyncPipe`, no `async` pipe or `ngModel` in templates, no `any`, no direct `@spartan-ng/helm/*` imports (use `@shared/spartan-ui`), no `@ngrx/*` imports except `@ngrx/signals` in `infrastructure/state` (spreads `infrastructureConventions`), `prefer-inject`, `prefer-standalone`, control-flow syntax. New apps/libs must spread `conventions` in their `eslint.config.mjs` (generated spartan-ui libs are exempt). Always run `npx nx lint <project>` and fix errors instead of disabling rules.

## Security and quality
- No secrets in code; no unsafe HTML (`innerHTML`, `bypassSecurityTrust*`); validate external input.
- Small focused functions, clear names, no dead code or debug output, no unrelated changes.
- Run lint/test/build through Nx (`npx nx ...`); never guess CLI flags.
